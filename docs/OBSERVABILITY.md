## Run it

```bash
cd services && mvn -B package -DskipTests && cd ..        # jars + the OpenTelemetry Java agent (from Maven Central)
PV_TRACING=true docker compose --profile observability up -d --build
```

| Tool | Address (local only) | What it holds |
|---|---|---|
| Prometheus v3.15.0 | http://127.0.0.1:9090 | scrapes `/actuator/prometheus` of the five services every 15 s; evaluates the alert rules |
| Grafana 13.2.3 | http://127.0.0.1:3000 | three read-only dashboards in the *PharmaVigil* folder (anonymous viewer, no login) |
| Jaeger 2.22.0 | http://127.0.0.1:16686 | traces from the OpenTelemetry Java agent 2.32.0 (OTLP over HTTP) |

Without `PV_TRACING=true` the agent stays attached but switched off (`OTEL_JAVAAGENT_ENABLED=false`).

## Metrics

Micrometer names (Prometheus shows dots as underscores; timers end in `_seconds`, counters in `_total`).

| Metric | Type, tags | Where | Meaning |
|---|---|---|---|
| `pv.reports.received` | counter; `source`, `kind` = new / follow_up / duplicate | intake-gateway | reports accepted, counted after the receipt commits |
| `pv.pipeline.stage` | timer (histogram); `stage`, `outcome` = ok / error | case-service | time to process one Kafka message per stage: dedup, coding, triage, narrative, submission-status |
| `pv.report.intake_to_coded` | timer (histogram) | case-service | intake-gateway's acceptance (stored on the case, `intake_received_at`) to the end of coding |
| `pv.pipeline.outcome` | counter; `stage`, `result` | case-service | coding: CODED / NEEDS_MANUAL_CODING; triage: SERIOUS / NON_SERIOUS / UNKNOWN / SKIPPED_IN_REVIEW |
| `pv.model.inference` | timer (histogram); `model` | case-service | ONNX Runtime time per call: meddra-coder, seriousness, duplicates |
| `pv.review.decisions` | counter; `field` = PT / SERIOUSNESS / DUPLICATE, `outcome` = accepted / corrected / manual | case-service | reviewer kept the model's suggestion, changed it, or there was none |
| `pv.outbox.backlog` | gauge | every service with an outbox | rows not yet published to Kafka (NaN while the database is unreachable) |
| `kafka_consumer_fetch_manager_records_lag` | gauge; `topic`, `partition` | Kafka client (Spring Boot) | messages a consumer still has to read per partition |
| `pv.jms.queue.depth` | gauge; `queue` = regulatory.outbound / regulatory.ack / DLQ | submission-gateway | messages waiting, by browsing the queue every 15 s (NaN while the broker is unreachable) |
| `pv.submissions.sent` | counter | submission-gateway | E2B(R3) messages put on `regulatory.outbound` |
| `pv.regulator.answers` | counter; `outcome` = ACK / NACK | submission-gateway | answers recorded (a redelivered answer is not counted twice) |
| `pv.signals.lookups` | counter; `result` = warning / none / no_data | signal-service | counter warnings requested at dispense |
| `pv.signals.snapshot.pairs`, `.loaded` | gauges | signal-service | size and load time of the signal snapshot (NaN without one) |

The *reviewer acceptance rate* is `accepted / (accepted + corrected)`. It is feedback from reviewers, not a
measured accuracy, and with the synthetic test bundle (model versions start with `fixture:`) it means nothing.

## Traces

The OpenTelemetry Java agent instruments HTTP, JDBC, Kafka and JMS. Two things needed code:

- **Through the outbox.** An event is written to `outbox_event` in the request's transaction and published later
  by a background relay, so the agent alone would start a new trace at the relay. Each row now stores the
  writer's W3C `traceparent` (`trace_parent` column, captured in `@PrePersist`), and the relay makes it current
  while it sends the row (`common/outbox/TraceParent`). Without the agent nothing is stored.
- **Service names** come from `OTEL_SERVICE_NAME` per container.

Checked on the local stack (`analysis/m10/trace_example.json`): the report sent by the Playwright smoke test
produced **one trace with 182 spans across pharmacy-service, intake-gateway and case-service**: the pharmacy
forwarder's HTTP call, `POST /api/intake/reports`, `report.received publish`, then `process` and `publish` for
report.received, report.deduped, report.coded and case.triaged in case-service.

Not checked yet: the JMS hop (submission-gateway → mock regulator → answer). A submission needs the official
E2B(R3) schemas, which this build container cannot download (CI can); the agent's JMS instrumentation is
expected to cover it, but no trace of it has been looked at.

Known noise: the outbox relays poll every 500 ms, and each poll's `SELECT … outbox_event` becomes its own small
trace in Jaeger.

## Dashboards (`ops/grafana/dashboards/`)

Generated by `ops/grafana/generate_dashboards.py` (one short description per panel; run it after a change).
Every dashboard carries the disclaimers. Screenshots from the local stack after the third k6 run:
`analysis/m10/screenshots/`.

| Dashboard | Panels |
|---|---|
| **Pipeline health** (`pv-pipeline`) | reports/min, intake→coded p95, max consumer lag, outbox backlog; reports by source; stage p95; stage failures; lag per topic; backlog per service; JMS queue depth; regulator answers per hour |
| **AI quality** (`pv-ai-quality`) | reviewers kept the coder / seriousness / duplicate suggestion; decisions per hour; model inference p95; coding results; triage results |
| **Safety signals** (`pv-signals`) | pairs in the snapshot, snapshot age, share of lookups with a warning, lookups per minute. Empty until a `pv-ml export-signals` folder is mounted (`SIGNALS_DIR`); no real export exists yet (FAERS hosts blocked), so it shows "No snapshot loaded" rather than invented numbers |

## Alert rules (`ops/grafana/alerts/pharmavigil.rules.yml`)

Prometheus evaluates them; Grafana lists them as data-source-managed rules. `promtool check rules`: 9 rules, OK.

| Alert | Fires when | What to do |
|---|---|---|
| PvServiceDown | a service is not scraped for 2 min | check its container logs |
| PvOutboxBacklogGrowing | > 100 unpublished events for 5 min | Kafka is down or unreachable; nothing is lost, events go out in order when it is back |
| PvConsumerLagHigh | a topic is > 1000 messages behind for 5 min | consumers are slower than intake; see stage p95 |
| PvIntakeToCodedSlow | p95 intake→coded > 60 s for 10 min | see stage p95 and the outbox backlog |
| PvPipelineStageFailing | a stage keeps failing for 5 min | look at the stage's `.dlq` topic |
| PvJmsDeadLetters | messages in the broker DLQ for 5 min | inspect them; the case stays in its last status |
| PvRegulatorNack | any NACK in the last hour | the case is back in review with the reason |
| PvCodingMostlyManual | > 50% of new cases need manual coding for 30 min | the coder is missing (`PV_MODEL_DIR`) or unsure |
| PvSignalSnapshotMissing | no signal snapshot for 1 h | mount a signal export |

## How the queries were checked

`ops/grafana/check_queries.py` runs every dashboard query and every alert expression against the Prometheus of the
running stack and writes `analysis/m10/dashboard_queries.json`. After the third k6 run: **31 queries, 0 failed,
19 returned data**. The ones without data are expected on this stack: no signal snapshot, no submissions (no
schemas locally), no duplicate decisions by the load-test reviewer, and alerts that were not firing.
